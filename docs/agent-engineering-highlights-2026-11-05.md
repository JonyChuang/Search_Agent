## 3. 亮点一：按预算装配上下文，保留任务事实与来源

场景：用户连续准备多家公司，历史包含简历、长 JD、面经、题目和网页内容；固定轮数仍可能装入过多 token，也可能丢失重要约束。

设计：
1. 每轮独立读取可信身份、工具权限和当前业务版本，不能从旧摘要继承权限。
2. 先装入任务目标、用户明确约束、当前材料版本、待处理步骤和最近完整交互。
3. 大段工具输入输出写入带用户归属、产物 ID 和版本的工作区。提示词中仅保留必要片段和可检索引用。
4. 根据模型窗口，扣除系统/工具定义、预留输出和工具结果空间，计算可用输入预算；计数适配模型 tokenizer，并核对 provider 实际 usage。
5. 超出预算时优先移出冗长原文，再对已完成的旧交互生成摘要。未完成的 tool_call/tool_result 配对保留，不能从中间裁断消息。
6. 摘要包含目标、决定、已完成步骤、未解决问题、产物引用、用户更正和下一步，区分已确认事实与推测。
7. 压缩前保存原始消息和工具结果。摘要丢失细节时按产物引用回查；摘要引用的简历或资料失效时重新取当前版本。
8. 压缩后检查关键约束和引用是否保留，并设置重复压缩检测。仍超预算时缩小检索或分页读取，不无限摘要。

完整简历和岗位要求的权威版本由 Java 管理；Python 管理上下文装配、摘要及工作区。摘要不能作为执行网申的授权，也不能改变用户事实。

建议入口（规划）：api/app/core/agent/context/{budget,assembler,compactor,artifacts}.py；对接 Java 的材料版本查询。名称在实施时可按现有模块调整。

验证：记录输入 token、压缩本身开销、总调用成本、任务质量、用户约束保留和来源定位情况。比较固定窗口、摘要和卸载结合方案，不只展示压缩率。

## 4. 亮点二：任务工作记忆与长期事实分层

| 信息类型 | 例子 | 存储与归属 | 生命周期 |
| --- | --- | --- | --- |
| 原始记录 | 用户消息、工具结果、作答 | 持久化消息/产物；Java 业务记录与 Python 运行轨迹分别负责 | 可回查，遵循用户删除与保留规则 |
| 工作记忆 | 当前面试问题、目标公司、当前网申步骤、运行摘要 | Python 检查点，绑定 user_id/conversation_id/run_id；Redis 只作热点缓存 | 按当前任务和会话恢复 |
| 已确认事实 | 科研贡献、项目结果、简历版本 | Java MySQL 权威数据 | 版本化；用户可修正、删除 |
| 偏好 | 目标岗位、地点、准备时间 | Java 配置或明确确认的偏好记录 | 可修改、撤销及设置有效期 |
| 长期经验 | 某知识点近期多次答错 | Java 作答记录支持的派生总结；Python 提取候选 | 保留依据、时间、置信与失效状态 |
| 检索索引 | 材料片段、可召回记忆 | Elasticsearch 派生索引 | 根据权威数据重建，不能充当最终事实库 |

不能只按“Redis=短期、MySQL=长期”划分。工作记忆也需要持久化，缓存丢失不能丢任务进度。

写入采用“候选提取 → 归属及来源校验 → 合并/版本处理 → 必要时用户确认”。模型对能力的推断不能写入为简历事实。检索先按用户、任务范围和有效版本过滤，再排序。

用户修改或删除资料后，更新版本与失效状态，撤销旧记忆和索引；最终装配再次核对当前版本，防止缓存或旧向量命中恢复已删除事实。索引更新失败进入重试状态。

验证：跨会话事实准确性、来源可追溯性、事实修改后的旧内容使用情况、删除传播、用户隔离。长记忆召回只作为依据，不凌驾于用户当前明确更正和权威事实。

## 5. 亮点三：工具治理贯穿 Python 与 Java

执行链：
意图与任务上下文 → 发现可用工具 → 参数结构校验 → 工具范围和业务授权 → 执行与幂等 → 结果校验 → 事件与成本。

Java 强制执行归属、数据版本、业务状态及写操作去重；Python 负责工具选择、声明校验、超时取消、结果归一化和反馈。页面直接调用业务接口时也执行相同规则。

工具分别标注只读、草稿写入、外部提交等性质。按用户当前授权与任务范围决定执行方式；低影响操作在既有授权内继续。需要本人处理的步骤保存状态，工具不能通过换名或其他 Skill 绕过业务限制。

Skill 和网页/文档内容不成为高优先级系统规则，不能扩展工具权限。Skill 包先支持流程与参考资料，不执行任意安装脚本；包版本、依赖、用户配置和运行版本分别记录。

缓存只对适合缓存的只读工具启用，键包含用户/权限范围、参数及资料版本；写操作通过业务幂等记录处理，不能用“同参数缓存成功”代替业务执行状态。

验证：参数错误、越权 ID、过期资料、技能缺依赖和工具失败有明确结果；确认未发生实际写入。网申的“材料已准备”“表单已填写”“站点已受理”分别判断。

## 6. 亮点四：有界并发、会话有序和失效执行者隔离

并发分为不同维度：
- 同一会话中会改变对话顺序的步骤串行，消息分配单调序号。
- 不同会话并行；独立只读子查询在依赖允许时并行。
- 同一个简历版本、网申记录或浏览器会话的写操作按资源顺序或乐观版本控制。
- 按用户、全局和模型供应商设置在途数量及请求/token 配额；队列有长度上限、过载响应和等待指标。

Python 单进程信号量只解决本进程并发。跨实例配额使用集中租约/原子计数等方案；Java 认领任务时保留执行代次。外部模型在请求超时后仍可能继续生成，需要记录不确定占用，不能把租约回收描述为供应商侧请求已取消。

锁持有者使用随机标识并通过原子比较释放，续租检查持有者。关键状态写入携带运行代次/版本，Java 拒绝已经失效的执行者回写；Redis 锁不承担最终业务唯一性。

数据库认领事务保持短小，不在行锁事务内等待模型。失败策略区分只读任务和有副作用任务：关键写入不能因协调服务不可用就无条件放行。

现有 agent_task.py 的固定锁值、finally 无条件删除及锁异常继续运行，应在迁移时按上述原则调整。多个读查询并发时注意避免并发共享不安全的数据库会话、citations 和 stats_holder；子任务独立结果收集后统一汇总。

验证：多实例同会话消息顺序、跨会话吞吐、过载排队、供应商 429、取消、租约过期和旧执行者回写。报告并发条件与错误率，不仅报告 QPS。

## 7. 亮点五：长任务持久化、可恢复执行与幂等

继续沿用 Java 架构文档的任务表与待派发记录，事务内保存，后台派发。消息和回调可能重复，使用 run_id/step_id/事件序号去重。

步骤检查点记录输入版本、工具调用、结果引用、当前目标、执行代次及下一步。恢复时从已确认步骤继续；对外部操作先核实回执和站点状态。

数据库写操作可以依靠唯一约束与幂等记录避免重复业务效果；外部网站无法承诺通用 exactly-once。网申结果不明时进入待核实或接管状态，不能直接回到“未提交”并再次点击。

SSE 只负责投递进度，数据库任务与持久化事件支持刷新查询和事件序号续传。Redis 实时消息丢失不等于历史结果丢失。恢复运行固定材料与 Skill 版本；不能保证模型文字完全一致。

验证故障点：任务提交后派发前、工具完成后记录前、模型调用中、用户接管期间、外部提交返回前、取消与完成并发。只对相关故障做验证，不堆积无意义的重复测试。

## 8. 亮点六：按需加载 Skill 与隔离子任务上下文

主会话先获得精简技能目录、适用范围和工具摘要，按需加载具体版本的 SKILL.md；参考资料单独读取。对工具多的场景只装配当前任务有权且可能使用的工具，记录发现和执行阶段。

比较多家公司等独立任务可使用子 Agent，父任务分配目标、材料引用、工具范围和子预算，回收结构化结果与证据。子 Agent 不默认继承完整用户历史，不把大量原始网页回填主会话。

父子预算合计约束总 token、工具调用和运行时间；父任务取消要向子任务传播。只读调查可并行，写入简历或网申等操作仍由 Java 业务服务协调。

首版先做单 Agent 与受控工具并发；有对照证据后再开启子 Agent，不通过固定角色数量宣称系统更强。

验证：技能选择适用性、工具定义占用、同任务单/多 Agent 完成质量、总成本、延迟和来源一致性。

- 面向长周期求职任务，实现按 token 预算的上下文装配，结合工具结果卸载、结构化摘要和原文回查，保留岗位约束与材料版本；使用固定任务集评估成本与任务完成质量。

- 基于步骤检查点和持久化任务事件实现任务恢复与前端续传，对网申等外部操作执行结果核对与人工接管。

性能或效果数字仅在对应测量完成后加入。源码来自 Comet 的原有能力与本次自行新增内容分别列清，不能把上游成绩或他人简历指标当作自己的成果。
